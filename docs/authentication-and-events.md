# Canvas authentication, events, and MCP integration research

Checked October 4, 2026 against local Canvas LMS commit `1c9f0bb8013ed69c4f2efe11fd483025469b7e6c` and current official documentation. Local Canvas source paths below refer to that separate reference checkout, not files bundled in canvas-mcp. This is engineering research, not a conclusion about every institution's deployment or legal advice.

## Recommended architecture

Build a separate, open-source Canvas API adapter with a small read-only MCP surface. Use the cloned LMS as the implementation reference and a possible local test fixture. A forked LMS is a new server, not a connection to the student's existing school data. Keep one credential-bound Canvas client per linked user and institution. Separate that user's app/MCP identity from their upstream Canvas identity. Key records by account + normalized Canvas origin + Canvas user ID; treat IDs as strings.

For local pilot use, an individually generated Canvas token may live in the user's environment/keychain. For a multiuser app use institution-approved OAuth developer keys and a hosted account-linking broker. The broker stores Canvas credentials and gives MCP clients audience-restricted tokens for our own server. An MCP token must not be a pass-through Canvas credential. Build polling and a normalized event outbox first; enable institutional Live Events as an optional accelerator. External files need their own provider adapters and authorizations.

## Canvas OAuth and PKCE

Canvas's [OAuth overview](https://developerdocs.instructure.com/services/canvas/oauth2/file.oauth) documents authorization-code OAuth at `/login/oauth2/auth`, exchange/refresh at `/login/oauth2/token`, and logout/revocation via DELETE. Hosted Canvas developer keys are issued by an institution's admin; self-hosted administrators create their own. The docs explicitly reserve manually generated tokens for testing and require OAuth for apps used by multiple users. A fork cannot grant itself access to an institution.

Use exact registered redirect URIs, unpredictable state, HTTPS, per-institution key lookup, secure refresh storage, and least-privilege route scopes. [Scoped developer keys](https://developerdocs.instructure.com/services/canvas/oauth2/file.developer_keys) constrain API routes, and a token still operates under the user's rights. Disabled keys/account bindings can invalidate access. Scoped developer keys also need “Allow Include Parameters” enabled for nested submission data; otherwise Canvas ignores include/includes parameters. Local sources: `doc/api/oauth.md`, `doc/api/oauth_endpoints.md`, and `app/models/developer_key.rb`.

The current source supports **S256 PKCE**, despite the older prose docs describing only client-secret exchange. `lib/canvas/oauth/pkce.rb` stores a challenge for ten minutes and validates the verifier. `lib/canvas/oauth/grant_types/authorization_code_with_pkce.rb` permits public clients; `base_type.rb` omits secret validation only when the developer key is explicitly a public client. `app/models/developer_key.rb:150` distinguishes public/confidential keys. Do not assume every institution can provision or has deployed this support; verify its registered client type and complete a real auth/refresh integration test.

Refresh behavior differs by client type. Confidential-client documentation describes one-hour access tokens and reusable refresh tokens. In this checkout `grant_types/refresh_token.rb` rotates refresh tokens for public clients and extends a rolling permanent-expiration window; `developer_key.rb:457` defaults nonmobile public clients to 120 minutes, while mobile behavior is separately configured. Store any replacement refresh token atomically, serialize refreshes per connection, and honor returned expiration. Avoid a universal “refresh forever” promise. Source links: [PKCE](https://github.com/instructure/canvas-lms/blob/1c9f0bb8013ed69c4f2efe11fd483025469b7e6c/lib/canvas/oauth/pkce.rb), [refresh](https://github.com/instructure/canvas-lms/blob/1c9f0bb8013ed69c4f2efe11fd483025469b7e6c/lib/canvas/oauth/grant_types/refresh_token.rb).

## What the mobile QR handoff actually does

The [official user guide](https://community.instructure.com/en/kb/articles/662904-how-do-i-view-a-qr-code-to-log-in-to-the-canvas-mobile-apps) says an already logged-in browser can generate a QR code for Canvas mobile apps; codes expire after ten minutes and institutions can disable the feature. A QR image is a temporary credential, not just an institution address.

Local `profile_controller.rb:596` requires both `InstructureMiscPlugin` and the account's QR setting. `ui/features/qr_mobile_login/react/components/QRMobileLogin.tsx` POSTs `/canvas/login.png`; the generating server implementation is not present in this checkout. The [official iOS GetSSOLogin source](https://github.com/instructure/canvas-ios/blob/master/Core/Core/Features/Login/GetSSOLogin.swift) accepts designated Canvas SSO hosts, extracts the institution domain and app-specific authorization code, requests mobile verification, and exchanges the code using the returned client configuration. [APIOAuth.swift](https://github.com/instructure/canvas-ios/blob/master/Core/Core/Features/Login/APIOAuth.swift) labels mobile verification as undocumented and models a client ID/secret response.

Trust crosses authenticated browser → QR possession → approved mobile client configuration → institution token endpoint. Our app should own its OAuth registration and pairing flow. Do not reuse first-party mobile client credentials, impersonate that client, or treat public client source as authorization to bypass school controls. A legitimate analogous UX is possible: finish approved OAuth in our browser UI, show a short-lived single-use pairing code for our own device/app, bind the redemption to a requesting device and explicit confirmation, and exchange it only with our broker. It is not the Canvas first-party QR protocol.

Canvas also documents [`GET /login/session_token`](https://developerdocs.instructure.com/services/canvas/oauth2/file.oauth_endpoints), which converts an already valid API token into a time-limited Canvas browser session URL for browser-only workflows. This does not supply missing API authorization or automatically authorize an external provider.

## Change detection and notifications

[Live Events](https://developerdocs.instructure.com/services/canvas/data-services/live-events/overview/file.data_service_introduction) is a subset of actions, intended for analytics; Instructure recommends the regular API when freshest state is required. [Subscription setup](https://developerdocs.instructure.com/services/canvas/data-services/live-events/overview/file.data_service_setup) supports AWS SQS or HTTPS with optional JWT signing. HTTPS has bounded retries and subscriptions may be disabled after sustained failures. Verify signed payloads against published rotating JWKs, queue before acknowledging, deduplicate, and refetch canonical resources under the linked user's authorization before emitting user-facing changes.

[Data Services administration](https://community.instructure.com/en/discussion/248030/getting-started-canvas-data-services-overview) requires account-level Data Services management permission and setup; ordinary student tokens do not automatically get subscriptions. The [plagiarism webhook API](https://developerdocs.instructure.com/services/canvas/external-tools/plagiarism-detection-platform/webhooks_subscriptions_for_plagiarism_platform) is purpose-specific, not a universal student webhook API. Local `doc/live_events.md` describes Kinesis emission and separate publisher/subscription/LTI services; cloning LMS alone does not supply a running hosted event service.

Polling fallback: sequential paginated reads of accessible assignments (including submission), announcements, and selected resources; hash material fields; establish the first baseline silently; emit created/changed observations after a fully successful snapshot; preserve the baseline after any partial failure. Do not infer deletion from missing visibility. Deduplicate by origin/user/resource/change version. Reconcile periodically even with webhooks. Local `doc/api/throttling.md` specifies cost-based quotas and `X-Request-Cost`/`X-Rate-Limit-Remaining`; back off on 429 and cap concurrency. `users_controller.rb:693` offers a user activity stream, but it is not a complete change log. Notification preferences control Canvas delivery preferences, not a general webhook subscription.

A local process can poll only while running and loses in-memory baselines after restart. Persistent scheduling/outbox storage is a distinct hosted feature. State this clearly in the pilot.

## General MCP and ChatGPT

Use standard MCP tools for on-demand reads; tool calls do not themselves create background jobs. Our service needs an explicit scheduler/subscription lifecycle for monitoring. Give clients canonical resource URLs and timestamps, and keep credentials outside model-visible results.

Current [OpenAI authentication docs](https://developers.openai.com/plugins/build/auth) require OAuth 2.1-compatible discovery, protected-resource metadata, S256 PKCE, resource/audience binding, and validated issuer/expiry/scopes. CIMD, DCR, or predefined clients are supported. Use the exact callback shown in management; callbacks vary according to issuer-identification support. These are the **MCP-facing** requirements; a broker adapts institution-specific Canvas OAuth behind them. Do not assume Canvas directly fulfills MCP discovery/registration/audience requirements.

Current [MCP Events documentation](https://developers.openai.com/plugins/build/mcp-events) supports event-driven Work chats on ChatGPT web, desktop Work with Cloud, and dots, subject to workspace controls. It requires MCP 2.0 (`2026-07-28`), persistent subscriptions, `events/list`, `events/subscribe`, `events/unsubscribe`, callback verification, and signed HTTPS webhook delivery. Therefore it is incorrect to claim ChatGPT can never react to pushed MCP updates. Bridge our normalized outbox to this interface where supported; keep ordinary read/poll tools for other hosts. ChatGPT's integration does not support polling/streaming delivery or draft gap/terminated controls. User authorizations, filters, expiry, replay policy, and revocation belong in the service, not just a prompt.

## External Google, Office, and LTI content

Canvas module items can be `ExternalUrl` or `ExternalTool` (`context_module_items_api_controller.rb:129`); HTML descriptions can also embed links. A returned link is not proof the linked document body is available through Canvas. Model a material as metadata + canonical source + provider + access state, and distinguish fetched content from unresolved links.

Google Drive needs its own OAuth scopes and file permissions; metadata-only scopes cannot download bodies, native Workspace files need export, and `capabilities.canDownload` matters. See [Google downloads/export](https://developers.google.com/workspace/drive/api/guides/manage-downloads) and [scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth). Microsoft Graph [file download](https://learn.microsoft.com/en-us/graph/api/driveitem-get-content?view=graph-rest-1.0) similarly requires delegated/application permissions and returns a temporary preauthenticated download URL. Do not send Canvas bearer tokens to either provider or arbitrary links; never persist signed URLs as durable identity.

LTI is a launch/service protocol, not a generic scrape/export API. Canvas OAuth docs restrict LTI service tokens to a tool's deployment context and related line items. Existing third-party LTI content may require a user browser launch, separate provider integration, and separate permissions. Report `requires_provider_connection`, `requires_browser`, or `unavailable` honestly.

## Source and license constraints

Canvas LMS's `LICENSE` is AGPLv3; iOS README says AGPLv3, Android README distinguishes GPLv3 applications and Apache-2.0 modules. Copying/adapting covered code is more than free use with attribution. The official [GNU AGPL text](https://www.gnu.org/licenses/agpl-3.0.txt), sections 4–6, requires preservation of notices/license and conditions for conveying modified source or binaries; section 13 adds an offer of Corresponding Source to remote users of a modified network-interactive version. The [GNU GPLv3 text](https://www.gnu.org/licenses/gpl-3.0.en.html), sections 4–6, similarly governs conveyed source/object code. AGPL network interaction should not be simplistically described as all use being distribution, nor as every independent API client automatically inheriting AGPL.

Keep upstream notices, record copied components and modifications, include build/install source needed for covered releases, and review actual composition/dependencies before selecting a distribution license. A newly authored API adapter is architecturally separable, but that alone is not a legal determination about copied code. The iOS [README](https://github.com/instructure/canvas-ios/blob/master/.github/README.md) also states that its PSPDFKit distribution licenses are not included. Open-source source does not provide hosted infrastructure, brand rights, first-party credentials, school data access, or third-party service licenses.
